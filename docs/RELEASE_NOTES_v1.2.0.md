## Summary

**v1.2.0 introduces a dual-radar dispatcher (BL-07).** Both the
v1.0.0 LD2420 firmware and the v1.1.0 LD2410 firmware remain
available on the GitHub Releases page, but the `main` branch
firmware is now a single dispatcher that can be configured for
either radar module via a per-node `substitutions.radar_type:`
key. New nodes pick their radar type at `scripts/new_node.sh
<name> [radar_type]` time; existing nodes continue to work
unchanged (the dispatcher is a strict superset of the v1.1.0
LD2410 firmware in terms of the resolved schema).

The v1.0.0 → v1.1.0 and v1.1.0 → v1.2.0 transitions are both
**per-node**. v1.1.0 → v1.2.0 is the safer one: the resolved
schema for an LD2410 node is identical to the v1.1.0 in-line
YAML, so a v1.1.0 firmware can be replaced by a v1.2.0
firmware over **OTA** (the API encryption key does not change).
For an LD2420 node, the v1.2.0 firmware is the first
LD2420-capable build since v1.0.0 — it must be flashed over
**USB** because the v1.1.0 firmware on the D1 mini does not
talk to the LD2420 module at all.

### What changed (v1.1.0 → v1.2.0)

| Area | v1.1.0 | v1.2.0 |
|---|---|---|
| Firmware entry | single in-line `firmware/radar.yaml` (LD2410-only) | per-node `firmware/radar.yaml` template + `firmware/_common.yaml.include` + `firmware/radar_ld2410.yaml` / `firmware/radar_ld2420.yaml` |
| Radar type selection | implicit (LD2410 only) | explicit per-node `substitutions.radar_type: ld2410` or `ld2420` |
| `new_node.sh` | `scripts/new_node.sh <name>` | `scripts/new_node.sh <name> [radar_type]` (default `ld2410`) |
| Preflight | single `MAIN_YAML` (LD2410 schema) | per-node YAMLs, `radar_type`-dispatched, `!include`-resolved |
| `components/ld2420_energy/` | unused on disk (v1.0.0 archive) | still on disk for v1.0.0 archive, loaded by `radar_ld2420.yaml` for v1.2.0 LD2420 builds |
| LD2420 firmware | not on `main` (only via `git checkout v1.0.0`) | first-class on `main` via `radar_ld2420.yaml` include |
| LD2410 firmware | yes | yes (unchanged schema) |
| openHAB entities | ~50 (LD2410) | ~50 (LD2410) / ~25 (LD2420) — same as v1.0.0 LD2420 entities |

### File layout (v1.2.0)

```
firmware/
├── _common.yaml.include       Platform-level (wifi/api/ota/logger/esphome)
├── radar_ld2410.yaml          LD2410-specific (uart, ld2410:, 9 gates)
├── radar_ld2420.yaml          LD2420-specific (external_components, ld2420:, 16 gates)
├── radar.yaml                 Per-node template (substitutions + packages:)
├── secrets.yaml.example
└── <node>.yaml                Generated by scripts/new_node.sh
```

### How to flash a new node (LD2410)

```bash
cd ~/dev/espRadar
git pull origin main
./scripts/clean.sh
./scripts/preflight.py    # must print "PRE-FLIGHT OK"
cd firmware
esphome run radar.yaml    # first flash via USB; later OTA from the dashboard
```

### How to flash a new node (LD2420)

```bash
cd ~/dev/espRadar
git pull origin main
./scripts/clean.sh
./scripts/preflight.py    # must print "PRE-FLIGHT OK"
cd firmware
esphome run radar.yaml
```

(The `radar.yaml` template's `substitutions.radar_type` defaults
to `ld2410`. For an LD2420 node, run
`scripts/new_node.sh kitchen ld2420` to generate
`firmware/kitchen.yaml` with `radar_type: ld2420` and the
matching `!include radar_ld2420.yaml` in the `packages:` block,
then `esphome run kitchen.yaml` to flash.)

### How to flash a second node (LD2410)

```bash
cd ~/dev/espRadar
./scripts/new_node.sh bedroom           # radar_type defaults to ld2410
# or: ./scripts/new_node.sh bedroom ld2410
cd firmware
esphome run bedroom.yaml
```

### How to flash a second node (LD2420)

```bash
cd ~/dev/espRadar
./scripts/new_node.sh kitchen ld2420
cd firmware
esphome run kitchen.yaml
```

Each node uses DHCP. Give every node a stable IP via
router-side MAC reservation (do NOT bake static IPs into the
firmware) — see the `## Network setup` section of README.md.

### How to revert a node to v1.0.0 (LD2420 hardware, legacy firmware)

```bash
cd ~/dev/espRadar
git checkout v1.0.0 -- firmware/livingroom.yaml components/ld2420_energy/
cd firmware
esphome run radar.yaml   # the v1.0.0 livingroom.yaml is checked in
git checkout main -- firmware/radar.yaml   # restore v1.2.0 YAML for the next node
```

The `components/ld2420_energy/` directory is kept in the repo
on `main` (v1.2.0) for this reason — the v1.0.0 firmware
expects it to be loaded via `external_components:`.

### How to revert a node to v1.1.0 (LD2410 hardware, pre-dispatcher)

```bash
cd ~/dev/espRadar
git checkout v1.1.0 -- firmware/radar.yaml
cd firmware
esphome run radar.yaml
git checkout main -- firmware/radar.yaml
```

The v1.1.0 release tag and SHA-256 are unchanged.

### OTA upgrade from v1.1.0 to v1.2.0 (LD2410 nodes)

The v1.2.0 firmware is a strict superset of the v1.1.0 firmware
in terms of the resolved schema for an LD2410 node. The API
encryption key is unchanged. The OTA partition is preserved
across the v1.1.0 → v1.2.0 upgrade. Flash the v1.2.0 firmware
from the ESPHome dashboard (OTA) or run `esphome run radar.yaml`
after pulling the new `main`.

### USB upgrade from v1.0.0 to v1.2.0 (LD2420 nodes)

A v1.0.0 firmware on the D1 mini does not talk to the LD2420
in the v1.1.0 / v1.2.0 schema. Flash the v1.2.0 firmware over
**USB**. The API encryption key changed in v1.1.0 (BL-06), so
the noise protocol handshake will fail with "handshake failure"
or "CONNECTION_CLOSED" if the v1.2.0 firmware's `api_encryption_key_`
is not the one in `firmware/secrets.yaml` — but for a fresh
LD2420 node, `scripts/new_node.sh <name> ld2420` generates the
right key from scratch.

**Reference for OTA verification.** Each tagged release has a
canonical `firmware.bin` SHA-256 that any later OTA payload
must match byte-for-byte:

| Tag | SHA-256 | Notes |
|---|---|---|
| `v1.0.0` | `fb0ea4f06ddc...398d3c` | LD2420, shared `api_encryption_key:`, UART 115200 |
| `v1.1.0` | `44c0e819ed3f...a2867` | LD2410, per-node `api_encryption_key_radar:`, UART 256000, 5V supply |
| `v1.2.0` (LD2410) | TBD | LD2410 dispatcher, packages:-based, identical resolved schema to v1.1.0 |
| `v1.2.0` (LD2420) | TBD | LD2420 dispatcher, packages:-based, 16 gates, `apply_config` button |

The v1.0.0 → v1.1.0 and v1.0.0 → v1.2.0 OTA upgrades **do not
work** (the noise session key is derived from the encryption
key on both sides, and the v1.0.0 firmware uses the legacy
shared key while v1.1.0 / v1.2.0 use per-node keys). A USB
re-flash is required.

The v1.1.0 → v1.2.0 (LD2410) OTA upgrade **does work** (the
resolved schema is identical and the per-node API key is
unchanged).
